# CC Cards Implementation Plan

> 在当前工作树逐项顺序执行。用户已确认卡片方式，后续补充恢复功能为同一任务的更新；不再增加批准步骤，不派发子代理。

**Goal:** 保留 CC 原功能与卡片切换，只限制新增外部供应商。
**Architecture:** 原生 catalog 组装平台分组服务卡片，Key 编辑/启动复用 CC 服务；原模块通过现有导航挂载。账户弹层移到根级。
**Tech Stack:** React / Tauri / Rust，既有 CC 组件及服务。
**Spec:** docs/superpowers/specs/2026-10-26-cc-cards-design.md

- [x] 卡片与策略：创建 aihubmix/tools.rs；工具服务列表、官方种子、Key 保存与启动；API 自动模型目录，删除模型选择 UI。测试官方准入/外部拒绝、无模型锁定、目录生成与 Key 不回传。
- [x] 导航与账户：恢复应用配置/MCP/Skills/提示词及原权限；会话用量保持原代码。充值、API 管理按 CC 导航行样式依次放在 MCP 上方；余额改在工具页右上角「添加分组」左侧纯展示。弹窗根挂载，修正空间/关闭/滚动。测试卡片操作、恢复导航、支付状态回归。
- [x] 平台分组卡片：支持添加未来分组；按 groupId 下拉筛选 active API Key；后台再次校验，选择和空卡片按账号持久化。API 管理复用列表及删除接口，增加确认和防重复提交。
- [x] 类型/fmt/定向及必要全量回归、本地构建、此前实机根层弹窗和真实工具路径验收。记录验证并提交。
- [ ] 最终“添加分组”实机点击复核：CUA 原生管道启动失败，重连无效；自动回归与最终包构建均通过，已在验证报告记录限制。

- [x] 修复真实 deepseek 平台类型被协议白名单过滤的问题；补全 deepseek/glm/zhipu 到 CC Chat 协议的适配，并用实际协议字段回归。

- [x] 最终分组规则：添加分组与申请 API 分开；只有当前账号持有 active API 的分组可添加，已添加分组可见但禁选，打开自动刷新，未来平台分组不靠品牌白名单。
