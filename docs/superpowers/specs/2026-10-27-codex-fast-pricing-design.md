# Codex Fast / Priority 用量估算支持

状态：用户于 2026-10-27 确认“补充吧”。

## 目标与范围

在现有 CC Codex 会话用量导入流程中识别请求发生时的服务档位，并使用对应的美元单价计算费用。普通与 Fast 请求混合的会话必须逐条计算。此次不发布，不调整 sub2api 定价、余额或扣费，也不执行对真实用户数据库的修复操作。

## 方案选择

采用逐请求识别服务档位并选择模型单价的方案，复用现有 Token 差量、去重、会话归属及统计流程。全局乘 2 会影响普通请求；改用平台账单则会改变 CC 的本地估算含义与数据来源，因此两者均不作为此次实现。

## 服务档位与价格

- 从 `turn_context`、`thread_settings_applied` 和用量事件中明确记录的服务档位恢复上下文；请求明确记录的档位优先于会话设置。
- 识别实际日志与协议确认的 Fast / Priority 值，区分“字段缺失”“恢复普通模式”和“未知值”，不从当前全局设置倒推历史。
- 每个用量事件携带当时的档位；切换模型或档位不重置 Token 累计基线，不改变请求标识与去重签名。
- 使用模型对应的 Priority 价格规则。已核对 GPT-6 / GPT-5.6 的 Sol、Astra、Terra、Luna 对应型号，以及 GPT-5.5、GPT-5.4、GPT-5.4 Mini、GPT-5.3 Codex、GPT-5.2、GPT-5.2 Codex、GPT-5.1 Codex 的 Priority 单价为标准价 2 倍；不得把这个倍率无条件应用到所有模型和其他服务档位。
- 价格规则需有明确的适用模型范围；无法确认模型 Priority 价格或历史档位时保留标准价估算，并以可识别的元数据保留估算依据，不伪造已知价格。
- 各费用分项与总费用使用同一档位的价格，仍存储美元。平台 0.3 倍折扣与人民币汇率不进入 CC 原价估算。

## 历史数据与兼容

为已导入的 Codex 会话补充档位及重算机制，使用现有同步和数据库事务模式保证幂等。仅更新能由原始日志确认的费用与档位元数据，不重复新增请求，不改变 Token 数、时间、会话归属和耗时。

保留明细的查询直接使用已修正费用，修正后通知界面刷新；后续汇总沿用修正结果。已经汇总并删除的旧明细无法可靠恢复原始导入集合，保留旧汇总，不重新导入。日志已不存在或无法恢复档位时保留已有数据；进程中断后可安全重试。禁止直接清空真实用量库。

档位通过现有 `pricing_model` 字段记录，服务档位价格按已核对模型的规则从标准价派生，不新增数据库列和模型种子行。历史修正进度使用本机 `session_log_sync` 保留行，按逻辑 rollout 文件名标记，与原同步游标分开；只修正 ID、模型及 Token 数完全一致的现有明细。

此次以 Codex 会话导入为范围，Claude、Pi 以及其他供应商继续使用现有计价行为。代理日志仍保留 CC 原有去重优先级，不通过 Token 指纹反推并改写代理账单；代理优先场景的服务档位采集属于后续独立工作。已核查本次用户报差异的用量全部来自 Codex 会话导入，无代理行覆盖。

## 验证

1. 相同 Token 下，两个已核对模型的 Priority 各费用分项与总费用为标准模式的 2 倍。
2. 同会话普通 → Priority → 普通，以及中途切换模型，归属与费用正确。
3. 字段缺失、显式恢复普通模式、未知档位或模型、重复快照、缓存命中和远程压缩用量事件保持正确处理。
4. 历史重算执行两次结果一致，Token、请求数量及去重保持不变；事务中断后重试安全。
5. 明细与汇总一致，其他 Agent 的现有测试继续通过。
6. 使用隔离测试数据库与日志副本验证，不修改本机真实用量库。

## 验收示例

对已确认全部为 Priority 的同一组请求，原标准估算约 $11.5 应更新为约 $23；这仍是美元原价估算。平台按 0.3 倍及约 6.6647 汇率扣费时约为 ¥46，最终逐笔对账仍以相同请求集合为前提。
