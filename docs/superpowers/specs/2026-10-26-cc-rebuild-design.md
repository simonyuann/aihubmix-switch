- 用户已取消按 WN Codex 截图重做界面；本次不新增截图工作台或替换 CC 导航。
- 目标仓库基线：`simonyuann/aihubmix-switch` 的 `origin/main`，提交 `617592d`，版本 `1.0.2`。本机另一工作目录仍为 `0.3.2`，不能以它作为迁移基线。
- CC 源码基线：`simonyuann/my-cc`，提交 `42ef63471f0ed879913f8de0d0c7e3e580293193`，版本 `4.0.20`，MIT 许可。

- 产品继续使用 AIHubMix Switch 品牌和现有服务配置；布局、导航、主题、组件和交互直接沿用 CC。

## 2. 方案选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A，采用 | 将 my-cc 的完整应用源码作为新基础，保留前后端和界面，增加 AIHubMix 业务扩展 | 直接继承 CC 功能与测试，减少自维护代码，方便持续对照上游 |
| B | 将 CC 的 Rust 模块逐个移入旧项目，保留旧 React 页面和统一 dispatch | 要长期维护两套状态、接口和兼容层，较难保证 CC 功能完整 |
| C | 保留旧实现，只按截图重做界面 | 外观改动少，但不满足后台完全采用 CC 的要求 |

按 A 设计。重构提交保留目标仓库 Git 历史，记录 CC 来源提交与 MIT 版权。my-cc 克隆仅作为源码参考，不修改其原分支。

## 3. 后端边界

### CC 核心

完整引入 CC 的 `src-tauri` 功能模块、数据库与迁移、原生配置读写、命令注册、代理和协议转换、工具检测与生命周期、授权中心、配置备份与还原、MCP、Skills、提示词、会话、用量、同步和配置档案。

保留 CC 已有的 13 种应用支持及能力差异：Claude Code、Claude Desktop、Codex、Gemini、Grok Build、OpenCode、OpenClaw、Hermes、Pi、MiniMax Code、Kimi、Antigravity、Oh My Pi。保持其已有功能入口。

前端通过 CC 原有的 `src/lib/api` 和查询 hooks 调用后端。供应商新增、切换、启动、模型、推理强度、代理和历史统一等行为走 CC 原有服务，不继续沿用旧 `agents.rs`、`agent_adapters.rs`、`bridge.rs`、`protocol.rs` 的平行实现。

### AIHubMix 扩展

CC 的 `auth` 管理 Codex、Claude、Copilot 等工具授权，不提供现有 AIHubMix 平台账户、平台 Key 或钱包充值接口；这些业务必须保留为独立扩展。

- 从 v1.0.2 提取平台登录、注册、刷新登录、退出、分组和 Key 管理、钱包余额、支付配置、订单创建/查询/取消等能力。
- 将这些能力组织为独立的 Rust 账户与支付服务、Tauri 命令和前端 API；不把旧 Backend 整体嵌回新项目。
- 平台访问令牌保留在 Rust 和系统安全存储中。支付订单继续遵守现有金额、账户归属和防重复提交约束。
- 选择平台 Key 后，形成 CC 的供应商配置，提交给 CC 的 provider 服务；所有目标工具文件写入、代理和启动继续由 CC 负责。
- 账户余额来自 `/api/v1/auth/me`，按服务返回的真实币种格式显示；钱包余额、Key 配额和 CC 用量统计分开建模。
- 现有可配置服务地址继续保留，不把 CC 内置的 `aihubmix.com` 供应商预设误认为当前 `csmy.fun` 平台服务。

## 4. 界面与导航

### 直接沿用 CC

完整采用 my-cc 的 React 界面，包括侧栏、供应商列表、设置、授权中心、应用管理和全局功能页。保留原有导航模型、主题、窗口布局、组件库、查询 hooks、托盘导航和深链接。

不新建工作台、顶部三栏导航或额外设计系统，不为品牌替换而批量重写 CC 组件、命令、内部模块名或数据库结构。

### AIHubMix 必要入口

- 在 CC 现有导航中增加单一的「AIHubMix 账户」入口，集中承载平台登录、钱包余额、Key 和充值；该入口不替换 CC 的工具官方授权中心。
- 新增业务页面和对话框使用 CC 已有 UI 组件与交互模式，不创建平行的组件库。
- 平台 Key 接入复用 CC 供应商添加与配置流程；补充必要的分组和 Key 选择后，由 CC 完成供应商管理和工具配置。
- 语言设置、工具安装与更新、模型与推理强度、官方登录、会话和高级功能使用 CC 原有入口。
- 仅调整面向用户的产品名称、图标、关于信息和产品链接，保留所需上游署名。

账户余额、币种和登录状态来自真实服务。加载、未登录、无数据和请求失败分别处理；刷新取消过期结果，账户切换后不展示上一账户的余额和订单。

## 5. 数据和升级

- 应用包标识保持 `fun.csmy.aihubmix-switch`，升级仍覆盖原应用。
- CC 管理数据使用 AIHubMix Switch 独立目录，通过 CC 的配置目录机制接入，避免默认写入用户现有 `~/.cc-switch`。设备设置路径和配置目录覆盖逻辑必须一并核对。
- 不修改 CC 数据库的 schema 版本或创建一套供应商表；使用其原有 schema 和服务。
- 首次升级提供旧版数据检测和可审阅导入：服务地址、可用的平台登录、本机 Key、工具与模型映射。新数据库写入使用事务，记录导入标记，重复启动不重复导入。
- 旧 `state-v2.json`、`vault-v2.bin`、`backups-v2/` 保留。安全存储无法解锁时提示重新登录或重新提供 Key，不能用空数据覆盖原 vault。
- 旧备份保留独立来源标记；不直接伪装成 CC 备份。提供打开旧备份目录及记录查看入口；旧版还原账本是否能转换由适配测试决定，不能无验证复用。
- 不在启动、预览或测试中自动改写用户真实工具配置和会话。导入后的工具生效仍使用 CC 的显式配置操作。

## 6. 构建、版本和上游同步

- 采用 CC 对应的 React、pnpm、Tauri 和 Rust 依赖及锁文件，避免强行把 CC React 18 组件移入旧 React 19 依赖树。
- my-cc 当前最低 macOS 版本为 12.0，高于旧产品的 11.0。本次采用 CC 的 12.0 下限，并在安装与更新适配中明确处理系统要求。
- 记录源码来源与产品改动，保留原 MIT 授权，产品版本采用 AIHubMix 自己的版本序列；构建元数据同步更新。
- 保留目标仓库更新公钥及现有下载站接口；必须核对 CC 更新器与现有签名/版本校验的契约，必要时保留小型产品适配层。
- 所有更新入口、便携版下载、关于页和发布脚本指向 AIHubMix 仓库或现有下载站，不能让客户端下载安装上游 CC Switch。
- CI 覆盖前端检查和 Windows/macOS/Linux 后端构建测试；安装包、签名、镜像检查沿用目标仓库已有约束，并适配新构建产物名。

## 7. 实施顺序和验收

1. 在独立分支导入 CC 基础，完成品牌、数据隔离、构建和更新配置，建立可编译的基线。
2. 接入平台账户、Key、余额与充值扩展，完成 Key 到 CC 供应商的转换。
3. 沿用 CC 全部界面，在现有导航和组件体系内接入 AIHubMix 账户入口与业务页面。
4. 实现旧版导入和错误恢复，核对完整更新与打包链路。
5. 运行适当的 CC 原有测试与新增集成测试，构建本机桌面应用，完成真实桌面交互核对。

验收重点：

- 界面布局、导航、主题和交互沿用 CC；产品品牌和新增账户业务来自 AIHubMix。
- CC 的 13 种工具和全局功能入口完整保留；涉及配置、代理、协议和启动的调用链能追踪到 CC 服务。
- 平台登录、Key 管理、余额刷新和充值使用模拟服务完成契约与账户隔离测试；不以测试为名创建真实充值订单。
- Codex 配置与文件凭据、模型/推理强度、官方授权、历史统一、切换回滚等关键路径有集成覆盖。
- 独立数据目录和测试目录生效；旧版导入失败可重试且不破坏原文件；不读写用户真实 `~/.cc-switch` 数据。
- 类型检查、受影响的前端与 Rust 测试、生产前端构建和本机桌面构建通过。其他平台是否验证通过以 CI 实际结果为准。
- 所有产品更新地址与签名配置均属于 AIHubMix；支付和账户请求不会占住 CC 代理的状态锁。
